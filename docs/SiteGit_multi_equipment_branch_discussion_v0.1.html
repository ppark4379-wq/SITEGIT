1. 논의 배경과 공통 전제

SiteGit의 핵심은 작업 결과를 바로 공식 현장 상태로 덮어쓰지 않고, 검증 가능한 Commit으로 남긴 뒤 관리자가 승인한 결과만 Main에 Merge하는 것이다.

01 · CONTEXT
데이터 전제현재 화면에 표시된 사상구 정비사업 목표량·잔여량·진척률은 UI 확인을 위한 임시값이다. 실제 데이터 계약과 산정 방법은 추후 교체하며, 이번 논의에서는 작업 Version 구조와 승인 흐름에 집중한다.
CURRENT FOUNDATION

현재 확보된 기반

  • 웹 자연어 Work Package 생성
  • Backend 작업지시와 Isaac Adapter 실행
  • 카메라·LiDAR·IMU 작업 전후 Evidence
  • Execution Commit 및 관리자 승인·반려
  • 승인된 Commit만 공식 웹 맵에 반영
CURRENT LIMIT

현재 구조의 한계

  • 장비 한 대의 Commit이 곧바로 Main 승인 대상
  • 동일 공정을 여러 장비가 나누는 개념이 없음
  • 장비별 부분 작업량과 공간 중첩 검증 부족
  • 작업 단계별 Branch와 최종 통합 Merge가 없음
  • Commit 기준 현장 타임라인 재생 기능이 없음

현재

Work Instruction → 장비 실행 → Commit → 관리자 승인 → Main

단일 장비 데모에는 적합하지만 다중 장비 협업과 공정 단위 인수에는 부족하다.

→

제안

Task Branch → 장비별 Commit → 통합 검증 → Branch 승인 → Main

장비별 책임과 Evidence를 보존하면서 공정 전체를 하나의 결과로 인수한다.

이번 구조가 해결해야 하는 질문

  1. 같은 구역을 여러 굴착기가 작업할 때 각 결과를 어떻게 구분하고 합칠 것인가?
  2. 각 장비 Commit은 언제 Clean, Warning, Conflict인가?
  3. 공정 전체가 어느 상태일 때 Main에 Merge할 수 있는가?
  4. 굴착·관로 설치·되메우기처럼 순서가 있는 공정을 어떻게 Version으로 연결할 것인가?

2. 제안하는 Branch 계층

Main은 공식 승인 현장 상태이며, 공정 단위 Task Branch 아래에서 장비별 실행 흐름이 독립적인 Commit을 생성한다.

MAIN

공식 현장 상태

관리자가 최종 인수한 작업만 존재한다. 웹의 기본 3D 맵과 공식 타임라인은 Main을 기준으로 렌더링한다.

TASK BRANCH

공정 단위 변경 집합

예: Zone C 토사 굴착. Work Package 목표, 공간 경계, 허용오차, 총작업량과 완료 조건을 소유한다.

EQUIPMENT LANE

장비별 실행 흐름

각 굴착기가 생성한 Commit을 장비 ID별로 묶어 보여주는 실행 단위다. 실제 Git 구현에서는 별도 Branch ref 또는 Commit metadata로 표현할 수 있다.

TASK MERGE COMMIT

통합 작업 결과

모든 장비 Commit을 합성하고 충돌을 해소한 공정 결과다. 관리자는 이 통합 Diff와 Evidence를 보고 Main Merge를 결정한다.

용어 주의“Branch 안의 Branch”는 사용자 화면의 계층 표현이다. 저장 계층에서는 모든 Commit을 하나의 DAG로 관리하고 task_branch_id, equipment_id, parent_commit_ids로 관계를 표현할 수 있다.

제안 기본 원칙

  • 장비 Commit은 Main을 직접 변경하지 않는다.
  • 장비 Commit 검토와 Task Branch 최종 Merge 검토는 서로 다른 단계다.
  • 반려된 Commit은 삭제하지 않고 해당 장비 흐름의 Conflict로 보존한다.
  • Task Branch가 완료되기 전에도 통합 예상 Diff는 미리 볼 수 있어야 한다.

4. Merge 및 Conflict 판정 제안

개별 Commit이 정상이어도 여러 장비 결과를 합쳤을 때 충돌할 수 있으므로, 장비 Commit Gate와 Task Branch Gate를 분리한다.

04 · MERGE
판정예시 조건시스템 동작
Clean할당 Polygon 내부, 다른 장비 결과와 비중첩, 필수 Evidence 완비, 목표 오차 이내Task Branch에 자동 통합 가능
Warning경계 인접, 일부 센서 품질 저하, 작업량 편차, 연결부 Height 차이통합 후보로 유지하고 관리자 확인 요청
Conflict동일 토사 중복 계산, 공간 중첩, 계획 경계 초과, 공정 순서 위반, Evidence 필수값 누락Branch Merge 차단, 재작업 Commit 요구

필수 Merge 검사 항목

① 공간 충돌

장비별 작업 Polygon, 안전반경, 작업 후 지형 영역이 겹치는지 검사한다.

② 물량 중복

같은 voxel/height cell의 절토량이 장비별 Commit에서 중복 집계되는지 확인한다.

③ 형상 연속성

장비 구역 경계에서 높이·경사·관로 연결부가 허용오차 내인지 확인한다.

④ 공정 의존성

굴착 완료 전 관로 설치, 관로 승인 전 되메우기 같은 순서 위반을 차단한다.

⑤ Evidence 품질

카메라 전후, LiDAR Point Cloud, IMU, 시간 순서와 좌표계 일치 여부를 검사한다.

⑥ 목표 충족

Task Branch 전체 작업량과 최종 형상이 Work Package의 완료 조건을 만족하는지 검사한다.

권장 2단계 승인

단계검토 대상결과
장비 Commit 검토해당 장비의 작업 전후 Evidence와 부분 DiffTask Branch 통합 / 재작업 / Conflict
Task Branch 검토모든 장비를 합친 최종 지형, 총작업량, 통합 ConflictMain Merge / Branch 반려
구현 원칙판정 규칙은 코드에 고정하지 않고 프로젝트별 정책으로 분리한다. 같은 공간 중첩도 측량 오차인지 실제 충돌인지에 따라 기준이 달라질 수 있으므로 허용오차와 필수 센서 목록은 Work Package 또는 Merge Rule Version에 귀속한다.

TIMELINE MODE

DIFF MODE

두 Version 비교

기준 Commit과 비교 Commit 사이의 절토·성토·객체 변경만 강조한다.

BRANCH MODE

승인 전 미리보기

Main과 Task Branch의 예상 결과를 비교하지만 공식 맵에는 적용하지 않는다.

성능을 위한 저장 전략

  • Baseline + Delta: 각 Commit에는 전체 맵 대신 추가·삭제·이동 Prim과 지형 변화량을 저장한다.
  • 주기적 Snapshot: 일정 Commit 또는 공정 Merge마다 전체 Height Map/Mesh Snapshot을 생성한다.
  • 근접 Snapshot 재생: 슬라이더 이동 시 가장 가까운 Snapshot부터 필요한 Delta만 적용한다.
  • 대용량 Evidence 분리: Point Cloud·이미지·Mesh 파일은 SSD에 저장하고 DB에는 storage key와 metadata만 둔다.

화면에서 Commit 선택 시 보여줄 정보

SiteGit은 장비 한 대의 작업 기록 시스템이 아니라, 여러 장비가 만든 물리적 변경을 Version으로 통합하고 사람이 Evidence를 근거로 공식 현장 상태에 Merge하는 시스템으로 정의한다. 구현의 핵심은 “장비 Commit은 Main을 직접 바꾸지 않는다”는 불변식을 유지하는 것이다.
